# Research: local agent capabilities and practical gaps

Checked **2026-10-05** against primary project documentation and ISHTI base commit `e9d2559`. This is a design comparison, not a benchmark or proof that another project is secure. File/line references describe that base; subsequent fixes are recorded in `MAC_CHANGES.md`. Effort estimates are engineering judgments: S = 1–2 days, M = 3–5 days, L = 1–2 weeks, including focused tests; they are not measured delivery promises.

ISHTI already implements most of the requested capability categories. Its valuable next work is to strengthen execution boundaries, recovery, evaluation, and integration. Replacing working skills with a different agent framework would increase migration risk without establishing better results on the owner's PC.

## Recommended first feature after safety repairs

Extend the current offline eval runner with **correction replay and a promotion report**. Seed it with English, Urdu, Pashto, conflicting corrections, disabled skills, and two synthetic clients. Test the actual routing path with stubbed model calls and disposable stores. The report should include dataset hash, base/candidate version, per-case expected/actual route, safety failures, and an explicit promotion verdict. Store it locally; do not run real skills while scoring routes.

Keep explicit corrections separate from inferred improvement candidates: an owner correcting their preference is evidence, while a model inventing a better policy requires evaluation. Rollback must deactivate only the selected candidate and preserve newer owner corrections. This improves the learning loop without changing model weights or adding GPU load.

## Hardware and adoption constraints

- **16GB VRAM:** serialize heavyweight model work; budget context/KV cache as well as model weights. Existing `taskmgr.gpu_slot()` and the model governor should remain the coordination points. A planner/executor split is a software role split, not a requirement to keep multiple large models resident.
- **64GB RAM:** CPU-side SQLite indexes, bounded histories, a browser, and parser subprocesses are reasonable architectural choices. This is a suitability judgment, not a measured capacity or latency claim.
- **Windows integration:** Job Objects, local CUDA/Ollama residency, voice devices, installed applications, Chrome Profile 9, and restart recovery are **NEEDS PC VERIFY**. No reference project was installed or benchmarked on this Mac.
- **Dependencies:** use stdlib/existing packages first. Borrow small design patterns instead of adopting whole runtimes. Defer new memory services, hosted browser subscriptions, online RL, multi-model swarms, automatic plugin installation, and automatic self-modifying code deployment.
- **Model identity:** retain all `ishti-*` custom models and existing model decisions. Any future model comparison must use local measurements and the project's full-residency check; research alone does not justify a replacement.

Research limitations: competitor capabilities above are documented claims, not independent tests. ISHTI capability presence is established by code inspection; live reachability, model quality, and all-PC-path safety are not established by that inspection. No benchmark rankings, resource measurements, or runtime correctness claims were inferred from stars, marketing, or README examples.
